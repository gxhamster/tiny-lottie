How do we know the different way to
read the data after an optimization has
been done in the encode stage. Some optimizations
can affect the way that the data will be read at the
decode stage. For example with the `nm` example after
we encode it as an uint8, we can't really read it back as
a string. What do we do then?
The most obvious thing that comes to mind is to have a flags
fields which store the optimizations done on a struct. Doing the
decode stage we can observe that and make the changes accordingly to
decoding.

If we hardcode the reading and writing of fields
how do we attempt to handle different versions
of lottie schema. (Original, LottieFiles Inc. version)
It does not need to be a fully generic solution as that
is thing we are trying to avoid. We want a more targeted
file format rather than one size fits all.
Do we have to change the read/write procedures for each
property that changes between the two schemas. Or can we find
a way to code-gen those stuff
What about stuff logic that needs to persist between the
two schema versions. Like optimizations of how we store
certain fields based on context.

I dont want to include reflection code in the encoding
systems. I beleive putting reflection code into a core part
of the system that is most likely to get linked from other
libraries is not a clean design. Make the code replicatable
from any other language

If we are passing a struct it becomes a little difficult to 
know what fields are set and what are not?

== Ways of appraoching writing optional fields ==
The most straight forward way I can think of is simply
to do some branches to check if each field exists. This is done
in the function body

if isset(flags, 0) do write_string(writer, vector_single.sid)
if isset(flags, 1) do write_bool(writer, vector_single.a)
if isset(flags, 2) do write_vector3(writer, vector_single.k)


Next method is to have a table of the offsets of each field
of the struct with the corresponding encoding function for each
field.

WriteFunc :: proc(writer: ^Writer, buf: []byte)
TblEntry :: struct {

v_single := PropVectorSingle{}
prop_vector_single_tbl := [?]TblEntry{

Another way of having a table is to do as below. Having a bunch of anonymous functions
defined inside each encoding funtion so that you can still have the type system available
and not have to do pass everything as rawptr's

write_prop_vector2 :: proc(writer: ^Writer, vector: PropVector) {
  Func :: proc(w: ^Writer, vec: PropVectorSingle)

  if vector_single, ok := vector.(PropVectorSingle); ok {
    write_tbl := [?]Func{
      proc(w: ^Writer, vec: PropVectorSingle) {write_string(w, vec.sid)},
      proc(w: ^Writer, vec: PropVectorSingle) {write_bool(w, vec.a)},
      proc(w: ^Writer, vec: PropVectorSingle) {write_vector3(w, vec.k)},
    }
    mask := extract_bit_indices(vector_single._flags)
    for idx in mask {
      if idx < len(write_tbl) {
        write_tbl[idx](writer, vector_single)
      }
    }
  }
}
